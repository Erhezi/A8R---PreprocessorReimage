Contract Atlas Preprocessor
Routes, services & overall design

Code snapshot: September 30, 2026 · Scope: the root run.py and preprocessorEC/ application, including current working-tree changes. The nested A8---Contract-Atlas/ project is outside this guide.

A quick developer reference for the task-based contract preprocessing app: how requests move through the system, where business logic lives, and which endpoints are available.

1. Overall design

The application is a Flask monolith organized by workflow phase. Jinja templates and Bootstrap render the pages; browser requests call JSON APIs for validation, matching, review decisions, and downloads. Quick Discovery is a separate, task-free lookup workflow in the same app.

Pages & browser requests→Blueprint routes→Services & state machine→Repositories / SQL
Layer / locationResponsibility
run.py and preprocessorEC/__init__.pyEntry point and create_app() factory. Load configuration, initialize sessions and database engines, register 11 blueprints, configure login, and attempt to load the sentence-transformer model.
preprocessorEC/<feature>/routes.pyHTTP input handling, authentication, JSON/file responses and page rendering. Routes delegate business operations to services; some also perform repository or SQL queries directly.
preprocessorEC/services/Validation, matching, scoring, review, dedup decisions and report construction. Many services are independent of Flask, but some helpers, including scoring and LLM review, read Flask configuration.
state.pyTaskState, phase/status constants and TaskStateMachine. Enforces forward transition guards and records phase changes. LangGraph is a future design target, not the current runtime.
db/task_repo.py, db/discovery_repo.py, models.pySQL Server persistence: tasks, input items, match snapshots, review decisions, issues, status history, discovery sets and prompt versions. Parameterized SQL also lives in feature queries/ directories and is loaded by db/sql_loader.py.
db/workstate_repo.py, common/session.pySQLite stores intermediate task state as JSON in instance/workstate.db; Flask sessions use a separate instance/session.db. SQLite tables are initialized by the app.
templates/, feature templates/, static/Shared layout, task and phase pages, embedded browser scripts and styles. The task detail page incorporates intake and preprocess content.

Data boundaries: SQL Server holds durable business records in the Preprocessor database. Queries also read shared CCX and Infor data through PLMPreprocessorShared. The dedup workspace (PreprocessorTaskItemForDecision) is an editable snapshot of accepted matches, separate from raw matching results. Phase changes update SQLite state, the SQL Server task record and the audit log in separate operations.

Access: workflow pages and APIs use Flask-Login sessions. Registration supports sourcing, mdm and preprocessor roles. Debug routes and Discovery prompt creation/activation require the preprocessor role; task contract registration has additional role checks. The admin route currently has a login guard only.

2. Main workflow

1 Intake→2 Identity→3 Preprocess→4 Dedup→5 Export→6 Monitoring
PhaseCurrent behaviorTransition guard
IntakeCreate a task; upload Excel/CSV rows; normalize fields; run PC1; correct, delete or manually pass eligible rows. Passing rows can advance while error rows are split into a child task.pc1_passed
IdentityCopy/apply standardized descriptions, select or confirm manufacturer information, enter contract details and run PC2.pc2_passed
PreprocessMatch CCX SKUs and score confidence; group contracts; cascade into Infor; optionally review with an LLM; match Infor residue; label Infor item numbers; validate buy UOM. Human decisions and issue resolution feed finalization.status == PREPROCESSED
DedupMaterialize accepted matches, choose keep/drop independently for each side, edit fields, and run kept-set integrity checks. Finalization marks dedup complete.status == DEDUP_COMPLETE
ExportPreview/download the dedup review workbook and mark contract replacements. Generic operational export formats remain a placeholder. Finalization advances to monitoring.status == EXPORTED
MonitoringShow current phase/status and transition history.No outgoing phase transition.

Matching choices: confidence scoring combines manufacturer number, description, price and packaging factors according to pair type. Tasks retain their threshold configuration, LLM prompt version and PAIR/GROUP review mode. Configuration B is the default (HIGH ≥ 0.90; MED ≥ 0.45). HIGH matches auto-accept; lower-confidence matches can receive LLM and human review. Match decisions use ACCEPTED, REJECTED and PENDING.

Quick Discovery: upload SKU + Description, optionally Supplier → match/rank CCX candidates → inspect or override verdicts → export. It uses its own sets/items/matches and database-backed prompt versions. The browser drives LLM work through start and repeated run-slice requests; each slice can run concurrent calls. Verdicts are SAME, DIFFERENT or UNCERTAIN.

5. Running & extending the project

  • Development: python run.py starts Flask in debug mode on port 5000.
  • Production: python run.py production serves through Waitress on 0.0.0.0:8090; the default blueprint prefix is /preprocessor.
  • Configuration: see config.py and .env.example. Configure SQL Server/ODBC, session secret, LLM connection settings and Discovery limits. SQL Server uses Windows trusted authentication. No credentials are included in this guide.
  • Database changes: SQL Server schema scripts live in migrations/, with relocation scripts under migrations/server_move/. The app factory creates SQLite working-state/session tables; it does not run the SQL Server migrations.
  • Model loading: startup attempts to load models/all-MiniLM-L6-v2, or download/cache it if absent. Failure is logged and fallback scoring remains available. The call happens during app creation.
  • Changes: start with the feature route and template, put reusable logic in services, and keep data access in repositories/query files where practical. Phase changes should use TaskStateMachine so guards and audit history stay aligned.
  • Verification: focused regression tests live in tests/, covering matching, decision batching, stale labels, LLM prompts and disconnect retries. This guide was checked against source; it is not evidence of a live database or deployment test.

For report interpretation, see the companion Contract reports guide.

6. Current implementation boundaries

Registered routes do not always mean a finished feature. The following distinctions come from function bodies, rather than older module comments.
  • POST /api/dedup/<task_id>/simulate returns not_implemented. The older dedup_service.validate_integrity() is also a stub, but the live /validate route calls the implemented integrity_check service.
  • Dedup finalization currently marks completion and advances; it does not itself rerun or enforce integrity checks.
  • POST /api/export/<task_id>/generate does not yet produce the generic batch_upload, single_contract or infor_direct files. Dedicated dedup-review, PC1 and Discovery workbook endpoints are implemented.
  • Item-master consequence lookups are scaffolded warnings, and monitoring currently reports history rather than implementing a background synchronization monitor.
  • Admin is a carried-over stub page. LangGraph/checkpoint integration remains a future direction; the current workflow is driven by Flask requests and a Python state machine.
Source reference: app factory, feature route decorators, state machine, service implementations, repositories and configuration in this working tree.
