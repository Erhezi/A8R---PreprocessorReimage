1. What is an acceptable contract price document?

Before we look at the reports, it helps to be on the same page about what a "good" contract price document needs to contain. The reports below are essentially asking "is this contract clean enough to load, and does it conflict with anything we already have on file?" — so the rules below are the yardstick.

1.1 The minimum information a contract must carry

Every line on a contract price file must answer six questions. If any of them are missing, we cannot load it cleanly:

QuestionWhat it tells usField on the file
Who are the contracting parties? Which Montefiore organization is buying, and which vendor is selling. Organization, ERP Vendor ID
Who makes the product? The manufacturer responsible for producing the item. Manufacturer, Mfg Part Number
What product is included? The unique part number assigned by the manufacturer. This is how we know two lines refer to the same product. Mfg Part Number
How do we order it? The vendor's catalog number, the unit of measure (UOM), the quantity that comes in that unit (QOE), and the price. Vendor Part Number, UOM, QOE, Contract Price
When does the price apply? The window during which this price is valid. Effective Date, Expiration Date
Which contract is this? The contract identifier that ties the line to a specific agreement. Contract ID
Why each field matters These contracts are what buyers' requisitions resolve against when staff order supplies across the hospital system. If a line is missing required information, or the identifiers/packaging are off, the requisition can fail to find the contracted item — and the order ends up bypassing the contract entirely (wrong price, wrong terms, or the item simply not pulled from the right agreement).

1.2 No duplicates from an ordering perspective

On a single contract, the same product in the same packaging should appear only once. "Same product, same packaging" means:

  • same Manufacturer Part Number, and
  • same UOM and QOE (so the unit you order is identical).

If the same product shows up twice on the same contract (e.g., two lines, same Mfg Part Number, same UOM, same QOE, possibly different prices), the system has no way to know which one to use when a buyer places an order. That has to be cleaned up before loading.

UOM aliases also count as duplicates Some vendors use codes like CS and CA interchangeably to mean "case" — the same physical packaging, just labeled differently on different lines. The system treats these as equivalent, so two lines with the same Mfg Part Number and the same QOE, one labeled CS and the other CA, are flagged as duplicates and need to be reconciled to a single line.

1.3 The "one item, one contract" guidance

Montefiore's general rule is: the same product should live on only one contract. A "contract," in this context, is the combination of three things together:

One contract = one (Organization, Vendor, Contract ID) trio Two lines that share all three of those values are on the same contract. Change any one of them and you are looking at a different contract.

Some additional nuance:

  • In some cases, a Member Entity (ME) organization and the MHS organization are carrying the same item on parallel contracts. That may need to be consolidated — usually onto the MHS-side contract — unless the organizations genuinely have different prices for the item.
  • When system constraints make it impossible to have a strict 1-product-1-contract relationship, the rule becomes: across all the contracts that carry the same product in the same packaging, the data elements (Manufacturer, Mfg Part Number, Vendor Part Number, UOM, QOE) must be consistent with each other. Prices may differ across contracts; the identifiers and packaging must not.

When 1-product-1-contract is genuinely not achievable

A few real situations force the same product onto more than one contract:

  • Two organizations, same vendor, different prices. Two organizations buy the same product from the same vendor but at different negotiated prices — each org needs its own contract line so its requisitions resolve to its own price.
  • Same product available from two different vendors. We want the option to buy from either vendor. Each vendor sits on its own contract.
  • Premier contract coexists with a better-priced local contract. We are obliged to keep the Premier line on file even when a local contract has a better price — so both have to remain.

What "consistent data elements" looks like in practice

The fields that have to match depend on why the duplication exists. A few examples:

  • Same vendor, two different prices for the same product (e.g., MHS vs ME pricing): Manufacturer, Mfg Part Number, Vendor Part Number, UOM, and QOE must all be identical across the two lines. Only the Contract Price (and the contract-header fields like Org and Contract ID) should differ.
  • Same product bought from two different vendors, same packaging: Manufacturer, Mfg Part Number, UOM, and QOE must be identical. The Vendor Part Number can legitimately differ, because each vendor uses its own catalog number for the same item.
  • Same product offered in different packaging (e.g., one contract sells it by EA, another by CS): Manufacturer and Mfg Part Number must be identical. UOM, QOE, Vendor Part Number, and price are allowed to differ to reflect the different packaging.

The common thread: Manufacturer and Mfg Part Number always have to agree — they are how the system knows two lines refer to the same product in the first place. Everything else can vary only when there is a legitimate reason.

1.4 A short glossary

Organization (Org)The Montefiore entity that the contract is signed for. Either MHS (the system-wide entity) or one of the Member Entities (ME).
MHSThe single system-wide Montefiore organization. There is exactly one MHS.
ME (Member Entity)Any Montefiore organization that is not MHS.
Premier contractA contract sourced through Premier (the GPO). Premier contracts cannot simply be dropped — even if a local contract has a better price, we are obliged to keep the Premier line on file.
Local contractA contract negotiated outside of Premier. These can be dropped if a better-priced or higher-priority alternative exists.
Manufacturer contract A contract signed directly with the company that makes the product. The "Manufacturer" field on each line is the same company we are buying from. These are the cleanest case — the manufacturer of the item is unambiguous.
Distributor contract A contract signed with a distributor (e.g., Medline, Cardinal, McKesson) who resells products made by many different manufacturers. The vendor on the contract is the distributor; the actual manufacturers of the products vary line by line.

Important CCX limitation: CCX does not, on its own, separate "vendor" from "manufacturer" on a distributor contract. Without further manipulation, every line on a distributor contract is loaded as if the distributor itself manufactured the item. That is factually wrong, and it creates problems downstream — Infor cannot always consolidate a contracted line to the correct Item Master record, which can cause buyer requisitions to bypass the contract or to land on the wrong item entirely.

The number of items affected can look small relative to the full contract, but Item Master items typically represent high purchase volume, especially inventory items. So the day-to-day operational impact is larger than the raw count suggests. When you see a distributor contract come through, the manufacturer columns deserve extra scrutiny.
UOMUnit of Measure (e.g., EA, BX, CS). Some vendors use CS and CA interchangeably for "case"; the system treats them as equivalent.
QOEQuantity Of Each — how many of the base unit are inside one UOM. A box of 10 has QOE = 10.
Contract Price (a.k.a. Price)The negotiated price for one UOM of the item on this contract. If UOM is BX and QOE is 10, the Contract Price is the price for one box of 10 — not per individual unit. Always read it together with the UOM and QOE on the same line, otherwise it's ambiguous.
EA pricePrice per individual unit. Computed as Contract Price ÷ QOE. This is what we use to compare two lines fairly when their packaging differs.
Input fileThe new spreadsheet you are uploading to load or update a contract.
CCXThe system of record we already have loaded. The dedup review compares your input against what's already in CCX.

2. The Dedup Review report

File name: dedup_output_to_review_<ContractID>_<VendorID>_<date>.xlsx

2.1 What this report is for

After you upload a contract file, the system compares each line on your input against every contract line we already have loaded in CCX. Whenever it finds an overlap — meaning the same product (Mfg Part Number) is present on both sides — it records that as a "match" so you can decide what to do. The dedup review report is the human-readable list of those matches.

The system never drops or merges anything by itself. It surfaces conflicts and recommends an action. You make the call.

2.2 The color code (this is on every sheet)

Yellow = data already on file in CCX (the "matched" side)
Light blue = data from your uploaded input file

If you only remember one thing about the colors: yellow is what we already have, blue is what you're bringing in.

2.4 The five "groups" — what kind of overlap each row represents

Every match row is classified into one of five groups. The group is reflected in the wording of the Action column. You don't see the group code itself — but understanding the five groups makes the Action column self-explanatory:

GroupWhat's the same?What's different?Plain-English summary
SS Same Source Org, Vendor, Contract ID, product Nothing — input line lands on a line that already exists on the same contract The input matched an existing line on the very same contract. Treat as an update to that line.
DV Different Vendor Product (Mfg Part Number) Vendor Same item being bought from two different vendors. Both lines stay by default.
ODO Other Org, Same Contract ID Vendor, Contract ID, product Organization Same contract product being used by two different organizations. If different pricing, both lines stay by default, if truely different in pricing, both lines have to stay.
TCCD Two Contracts, Same Org, Same Vendor Org, Vendor, product Contract ID Same org buying the same item from the same vendor on two different contracts. The classic "consolidate or pick one" case.
CECCD Different Org and Different Contract Vendor, product Org and Contract ID Two different organizations, each with their own contract for the same product. Consolidation or leave as it-is depending on pricing.
SS overlaps when you're adding new items to an existing contract If your input is meant to add new items to a contract that already exists, any SS rows you see are not pure renewals — they are products that already sit on the contract you are loading into. Don't ignore them. Review each SS row and decide whether to:
  • update the price on the existing line, if your input has a newer price; or
  • remove the existing line, if it's being superseded; or
  • drop the line from your input, if the existing one is correct as-is.
Letting both stand without review is how you end up with conflicting duplicate lines on the same contract.

2.5 Reading the Action column

The Action column is the system's one-line recommendation. The exact wording depends on whether your input line is doing an UPDATE/NEW or an EXPIRE.

If the input isUPDATE / NEWEXPIRE
SS Same contract item, Update Same contract item, Update expiration date to expire
DV Buy from different vendor, keep both Not affected by expiring the input line, keep the record
ODO Buy for different organization using same contract ID, review Not affected by expiring the input line, keep the record
TCCD Consider only keep one record, review Not affected by expiring the input line, keep the record
CECCD Buy for different organization using different contract, review Not affected by expiring the input line, keep the record
"Review" means a human decision is required. The system has flagged a real overlap and is telling you it doesn't have enough business context to pick a side. Use the Notes column for guidance.

2.6 Reading the Notes column

Notes is empty for SS, DV, and any EXPIRE row — those cases are unambiguous. Notes is populated for ODO, TCCD, and CECCD on UPDATE/NEW rows. The wording captures the two business levers that drive the decision:

  • Price comparison — is the existing CCX line cheaper, the new input line cheaper, or are they equal? Comparison is on EA price (Contract Price ÷ QOE), so packaging differences are normalized out.
  • Premier protection — if one side is on a Premier contract, we are obliged to keep that side. Premier lines cannot be dropped just because a local contract has a better price.

ODO — same contract, different organization

Two cases, price doesn't enter:

  • Both sides are ME: Different member entity contract item, keep both and make sure the data elements are consistent with each other.
  • One side is MHS: If not for tracking price difference between member entity and MHS, consider maintaining only the MHS contract and removing the member entity contract entirely. Otherwise, keep both and make sure the data elements are consistent with each other.

TCCD — same org, same vendor, two different contracts

The decision is shaped by price relation × (matched contract type, input contract type). The underlying logic:

  • Prefer the cheaper contract. If both are local, drop the more expensive side.
  • Premier overrides cheaper. If the side that would be dropped is a Premier contract, we go back to Premier to make a custom tier that reflect the desirable lower price (*as of 2026 May Policy Guidance, may change in the future)
  • Equal price, both local: the spec defers to the reviewer ("review and keep only one record") — this is a judgment call.

CECCD — different orgs, different contracts

Three sub-cases based on the org pair:

  • (ME, ME): always keep both — different member entities can legitimately maintain separate contracts. When prices differ, the note will ask you to verify that the price gap is real.
  • (MHS, ME) or (ME, MHS): prefer the MHS-side line when prices match. If prices differ, the spec asks you to first verify the gap is genuine before falling back to "drop the ME line."
  • Premier protection still applies. If dropping a side would mean dropping a Premier contract, go back to Premier to make a custom tier that reflect the desirable lower price (*as of 2026 May Policy Guidance, may change in the future).
  • (MHS, MHS) cannot happen — there is only one MHS organization.
How to act on a Notes recommendation
The notes use phrases like "consider keep X and drop Y", "keep both and ensure data elements are consistent," and "verify the price difference is real." These are guidance, not orders.

When the note says "keep both and ensure data elements are consistent": confirm that both lines have the same Mfg Part Number, Vendor Part Number, UOM, and QOE. Prices may differ; identifiers and packaging may not.

When the note says "consider keep X and drop Y": this is the system's recommendation under the standard rules. Override it only if you have a specific business reason.

When the note says "verify the price difference is real": confirm with the vendor or the contract documents that the gap is intentional, not a data-entry error.

2.7 The "to-be-replaced" special case

If your input file is replacing an existing CCX contract (rather than just updating it), the per-contract sheet for that CCX contract will also include rows for items on the old contract that did NOT match anything on your input. These rows carry:

  • Action: "Only seen on to-be-replaced contract <ContractID>"
  • Notes: "Check if the item is discontinued, or evaluate if we need to put this on the new contract."

This tells you what you would lose if the replacement went through as-is. For each such row, decide whether the item is genuinely going away (discontinued / no longer ordered) or whether it needs to be added to the new contract before you load it.

2.8 A worked example

Suppose your input file has 3M part number 1860 at $42.00/box of 50, on contract NEW-2026-001, organization MHS. CCX already has 1860 at $45.00/box of 50, on contract OLD-2024-099, also organization MHS, also vendor 3M. Both contracts are local.

  • Group: TCCD (same org, same vendor, different Contract ID).
  • Action: Consider only keep one record, review.
  • Notes: Input contract has better price, both are local contract, review and keep the input record and drop the matched line.
  • What you do: Confirm OLD-2024-099 can be expired for this item, and let the input load. The two lines have identical Mfg Part / UOM / QOE, so packaging is not an issue — only price.

Now flip it: same scenario, but the existing CCX line is on a Premier contract. The action is the same, but the note now says: "input contract has better price, but matched contract is premier while input contract is local, go back to Premier to make a custom tier on matched contract OLD-2024-099 reflecting the desirable lower price of the input contract." Per the May 2026 policy guidance, the Premier side cannot be dropped — instead, work with Premier to add a custom tier on OLD-2024-099 at the input's lower price, then let the cheaper line load against that updated tier.

3. The Pre-Check report

File name: precheck_report_<ContractID>_<VendorID>_<date>.xlsx

3.1 What this report is for

The pre-check runs before the dedup logic. Its job is to look at the input file on its own and answer one question: is this file clean enough to be loaded? Issues like missing required fields, malformed prices, duplicate items inside the same file, or vendor IDs that don't exist in our system show up here.

If the file has too many issues to fix one-by-one in the web UI, you will receive the excel report, fix the underlying spreadsheet offline, we will re-upload and proceed.

3.2 Errors vs. warnings

Errors must be fixed before the file can be loaded. A line with an error will not move past the pre-check.
Warnings are issues you should review but won't block the load. The system has applied a default or made a reasonable assumption; you should confirm it's correct.

Common warning examples include unusual UOM/QOE combinations and duplicate manufacturer or vendor part numbers within the input file that the system has automatically reduced to a single line.

3.4 The "header-level issues" row (Input Ref = 0)

Some problems are not tied to a specific line — for example, an unrecognized ERP Vendor ID, or a missing contract effective date. These are reported as a single synthetic row at the top of the report with Input Ref = 0 and Description = "(header-level issues)".

If you see one, fix the contract-level fields before worrying about line-level issues.

3.5 How to use the report

  1. Sort or filter by "With Error (Y/N) = Y" first. Address every error before re-uploading. Errors are non-negotiable.
  2. For each error row: read the Error Notes column for the human-readable explanation. Use the Input Ref column to find that exact row in your original spreadsheet. Fix the cell, save, and move on.
  3. Then review the warnings. A warning means the system loaded the line but applied a default or condensed duplicates. If the default was wrong, fix it; otherwise leave it.
  4. Re-upload the corrected file. The pre-check runs fresh against the new upload — you should see the error count drop. Iterate until "With Error (Y/N) = Y" returns zero rows.
Working efficiently when there are many errors Group your fixes by error type. If you have 50 rows all complaining about MISSING_QOE, fix them as a batch — the underlying cause is usually the same column missing in your source data.

3.6 What "good" looks like

  • Every active line has Total Error Count = 0.
  • The header-level row (Input Ref = 0) does not exist, or has no errors.
  • Any remaining warnings have been reviewed and confirmed to be acceptable defaults (e.g., the QOE/UOM combo is unusual but correct).

When you can say all three of those, the file is clean enough to move past pre-check. The dedup review (Part 2 of this guide) is the next stop.
